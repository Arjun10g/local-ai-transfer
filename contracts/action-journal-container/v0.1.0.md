# Fixed ActionJournal container layout v0.1.0

This contract defines only a fixed-size crash model for a future native
ActionJournal store. It does not add a Windows helper, file backend, IPC,
transport, package entry, process, production import, or runtime availability.
Both the merged wire protocol and current production ActionJournal remain
unavailable on Windows.

## Fixed layout

The container is exactly 33,558,528 bytes. A 4,096-byte immutable header is
followed by 1,024 logical slots. Each slot contains two 16,384-byte copy-on-write
banks. A bank consists of a 15,360-byte body and a separate 1,024-byte marker.
The body has a 1,024-byte descriptor and sixteen 896-byte event cells. Each
cell holds a four-byte little-endian length, the 32-byte merged v0.1.0 protocol
event digest, at most 768 canonical event bytes, and zero padding.

All integer fields use little-endian encoding. All unused, reserved, and padding
bytes are zero and are checked. Arithmetic is checked before offset calculation,
the file size is exact, and an operation refuses before writing if any length,
count, offset, generation, or capacity bound fails.

The header fixes the layout version, byte order, exact sizes and caps, merged
`lae.action-journal.v0.1.0` protocol identity, checksum algorithm, and a
non-secret 32-byte container ID. Its final 32 bytes authenticate the preceding
4,064 bytes using the formula in the machine contract. Initial formatting is
allowed only on a new, exact-size, all-zero container. It writes, flushes, and
reads back the entire header and never repairs or overwrites ambiguous existing
authority.

## Bank contents and protocol binding

Every committed bank contains the full history for one operation: one to
sixteen exact wire-protocol event projections, beginning at sequence zero with
`prepare`/`prepared`. Subsequent events must follow the merged protocol's exact
action, state, resolution, authorization, and sequence rules. The operation ID
is fixed in the bank descriptor. Event bytes must be strict UTF-8 canonical JSON
and their stored 32-byte digest is exactly:

```text
SHA-256("lae.action-journal.v0.1.0" || NUL || "event" || NUL ||
  canonical-event-json)
```

The descriptor also binds the event count, total used bytes, aggregate event
digest, final event digest, slot, bank, operation ID, and unsigned 64-bit
generation. The committed marker binds the checksum of the entire fixed bank
body, its predecessor generation, and predecessor committed-marker digest to
the container ID. A transplant between containers, slots, or banks therefore
does not validate.

## Copy-on-write commit protocol

Exactly one writer owns the future identity-held native file. To append one
event it writes the complete next history into the inactive bank:

1. Validate the old authority, exact one-event extension, transition, caps,
   generation, sizes, and offsets before any write.
2. Write a checksummed `STAGING` marker for the next generation to the inactive
   bank, call `FlushFileBuffers`, and read it back exactly.
3. Write the entire fixed 15,360-byte body, call `FlushFileBuffers`, and read
   back and validate the complete body.
4. Replace the marker with a checksummed `COMMITTED` marker containing the body
   digest, call `FlushFileBuffers`, and read back and validate the complete
   committed bank.
5. Acknowledge the append only after the final readback succeeds.

A process crash before a flush loses the volatile write. A crash after a valid
staging-marker flush leaves an explicitly inactive next bank, so startup keeps
the previous committed bank and ignores the staged body's contents. A torn or
malformed marker is ambiguous and fails closed; this source model does not
assume atomic sectors. A failure after the committed-marker flush may leave the
new bank authoritative even if the caller did not receive success, so callers
must reopen/query and must not replay a provider action.

The inactive bank's generation is exactly the current generation plus one and
its marker binds the current commit digest. Generation zero has the unsigned
64-bit maximum sentinel and a zero predecessor digest. Generation
`2^64 - 1` is readable, but another append is refused before any write.

## Startup selection and refusal

Startup validates the immutable header, then both markers in every slot. An
unused bank has an all-zero marker and body. A valid staging bank can be ignored
only when its predecessor relation is exact. A committed bank is authority only
after its marker, full body checksum, descriptor, event cells, canonical event
digests, and history all validate.

With two committed banks, the higher generation must be exactly one greater,
bind the lower commit digest, name the same operation, and extend the lower
history by exactly one event. Equal generations, gaps, divergent histories,
mismatched predecessor bindings, malformed markers, orphan bodies, duplicate
operation IDs in different slots, or conflicting authority fail closed.

The highest valid committed bank is selected. The container refuses more than
256 nonterminal records, 768 terminal records, 1,024 total records, or sixteen
events in one record. It does not silently prune, wrap, repair, or overwrite.

## Proof boundary

`tests/reference/action-journal-container-model.mjs` is a deterministic sparse
in-memory block-device model. It is implementation-independent test support,
not a filesystem implementation. It models volatile writes, explicit flushes,
partial flush persistence, power loss, readback, corruption, and restart.

A later Windows slice must hold a precreated file and directory identity for the
helper lifetime; validate current owner, private DACL, reparse state, file ID,
volume, link count, exact size, and path/handle identity; deny write/delete
sharing; perform complete checked-offset writes; call `FlushFileBuffers` at
every stated barrier; authenticate/cancel IPC; and pass exact-Windows crash and
fault acceptance. Until that work, packaging, trust-anchor review, independent
audit, and target evidence are complete, production availability remains false.
