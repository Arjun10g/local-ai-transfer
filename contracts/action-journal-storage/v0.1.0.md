# Inert Win32 ActionJournal storage boundary v0.1.0

This source-only contract narrows the future Windows filesystem boundary for
the merged fixed ActionJournal container. It does not add a helper executable,
IPC, Node integration, a CMake target, a package entry, or production
availability. The production ActionJournal availability flag remains false.

## Fixed request and lifetime

The only caller-selected values are an absolute storage-directory path, one of
`create_new` or `open_existing`, and—only for `open_existing`—a trusted exact
identity tuple consisting of volume serial, 128-bit file ID, and 32-byte
container ID. The leaf is always `action-journal-v1.container`; the caller
cannot supply another name, stream, extension, or relative path.

The directory must already exist with a protected, explicit DACL owned by and
granting one non-inherited `FILE_ALL_ACCESS` ACE only to the current process
token's non-service user SID. The implementation opens every existing ancestor
with `FILE_FLAG_OPEN_REPARSE_POINT`, rejects every reparse point, and retains
the handles with delete sharing denied. It opens the leaf with write and delete
sharing denied and retains that handle for the lease lifetime. A path is used
after acquisition only once, while all of those handles are held, to reopen the
fixed leaf and prove the exact volume/file ID and final path again. All content,
size, header, flush, and later storage operations are handle based.

Only an exact canonical drive-letter path on a `DRIVE_FIXED` NTFS volume with
persistent ACLs is eligible. UNC, device, extended, relative, normalized-alias,
ADS, slash, dot-component, trailing-dot/space, network, removable, RAM-disk,
optical, read-only, compressed-volume, non-NTFS, reparse, directory, device,
offline, sparse, compressed, encrypted, recall, virtual, linked, or
delete-pending objects fail closed.

## Genesis and strict reopen

`create_new` uses `CREATE_NEW` and an absolute private security descriptor in
the creation call. The new file must initially be empty. The boundary writes
and flushes the complete fixed 33,558,528-byte zero image, reads every byte
back as zero, obtains a nonzero 32-byte container ID from the system-preferred
CNG RNG, encodes the exact 4,096-byte merged container header and domain-separated
SHA-256 checksum, writes and flushes it, and strictly reads it back. A failure
after creation leaves the partial file in place for explicit recovery; the
boundary never deletes, truncates, repairs, or retries over ambiguous genesis.

`open_existing` uses `OPEN_EXISTING`, requires the exact trusted identity tuple,
requires the fixed size, and strictly validates the immutable header and
container ID. It does not accept identity copied from the candidate path as its
own trust anchor. Bank/event decoding remains owned by the merged container
codec and is an activation prerequisite, not part of this storage slice.

Success returns only finite status plus non-secret identity metadata. It never
returns or logs a path, SID, user name, security descriptor, content, or
free-form operating-system error. The retained lease is the authority; a
receipt without a retained handle cannot authorize use.

## Official Win32 assumptions

The source relies on these Microsoft-documented API contracts:

- `CreateFileW` sharing and `FILE_FLAG_OPEN_REPARSE_POINT` behavior:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew>
- final handle path resolution with `GetFinalPathNameByHandleW`:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew>
- handle metadata classes through `GetFileInformationByHandleEx`:
  <https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex>
- handle-based owner/DACL retrieval with `GetSecurityInfo`:
  <https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo>
- protected-DACL control semantics:
  <https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-control>
- handle-associated volume/filesystem metadata:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew>
- fixed/removable/network drive classification:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew>
- removable/hot-plug storage classification:
  <https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-storage_hotplug_info>
- system-preferred CNG random generation:
  <https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom>
- explicit file-buffer flushing:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers>

Those API contracts do not prove physical-media durability, antivirus or
filter-driver behavior, SDK compatibility, ACL behavior on the Dell target, or
power-loss safety. Remote Windows compilation/static analysis and exact-target
crash/storage acceptance remain mandatory before any integration or activation.
