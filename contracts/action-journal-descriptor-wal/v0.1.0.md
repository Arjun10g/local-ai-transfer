# Inert Win32 DescriptorActionJournal WAL boundary v0.1.0

This is a dormant, source-only contract for the v2 `DescriptorActionJournal`
write-ahead-log boundary in `native/action_journal_storage/windows_storage.cpp`.
It adds no helper executable, IPC, Node integration, product or default CMake
target, package entry, environment publication, or production availability.
Every availability gate in `v0.1.0.json` — `production_available`,
`native_target_registered`, `helper_added`, `transport_added`,
`node_integration_added`, `package_added`, and `activation_permitted` — is
literal `false`.

## Why this contract exists

[ADR-0004](../../coordination/adrs/ADR-0004-inert-contract-additive-extension.md)
permits additive status-code and predicate extensions to an inert,
activation-refused, transport-less contract without a version bump, and it
applied that rule to the four descriptor-WAL refusal statuses that were added
to `contracts/action-journal-storage/v0.1.0.json` under ICR-RUN-WDJB-001. The
same decision attaches a standing obligation:

> A separate frozen contract — for example
> `contracts/action-journal-descriptor-wal/` — is REQUIRED for the v2 WAL
> boundary before any transport, import, package, or activation path exists.

This file and `v0.1.0.json` discharge that obligation. **This contract is
required by ADR-0004 before any transport, import, package, or activation path
for the v2 WAL boundary, and no such path exists today.** `acquire_descriptor_wal`
has no callers; `lae-host.mjs`, `host/agent/action-journal.mjs`,
`host/agent/native-action-journal-client.mjs`,
`native/windows_supervisor/authority.cpp`,
`native/action_journal_helper/pipe_server.cpp`, and `native/CMakeLists.txt`
do not reference it. Adding the first such path is the event that makes this
contract load-bearing; it is not a licence to add one.

The v1 fixed-container lease keeps
`contracts/action-journal-storage/v0.1.0.json` as its authority. The two
boundaries share one translation unit today only because neither can be
reached. That contract retains a documented superset of the status codes
declared here; see `contracts/action-journal-storage/v0.1.0.md`. This contract
changes nothing in it.

## Fixed request and lifetime

The only caller-selected values are an absolute storage-directory path, one of
`create_new` or `open_existing`, and — only for `open_existing` — a separately
trusted `{volume_serial, file_id}` tuple. The leaf is always
`action-journal-v2.wal`; the caller cannot supply another name, stream,
extension, or relative path. Identity read from the candidate path may never
authorize its own reopen.

Acquisition reuses the storage boundary's canonical local fixed-NTFS,
retained no-follow ancestor, owner-only protected DACL, single-link,
non-delete-pending, stable volume/file identity, and final-path checks. Every
`CreateFileW` call in the translation unit sets
`SECURITY_SQOS_PRESENT | SECURITY_ANONYMOUS`. The retained leaf handle denies
write and delete sharing for the complete lease lifetime; that share-mode lease
is the exclusive-writer boundary against every other process.

`create_new` publishes only the exact 48-byte header
`{"format":"lae-action-journal-wal","version":2}\n`
(hex `7b22666f726d6174223a226c61652d616374696f6e2d6a6f75726e616c2d77616c222c2276657273696f6e223a327d0a`),
flushes it, reads it back, and asserts the published size is exactly 48 rather
than assuming it. The bound is 33,554,432 bytes inclusive. Both constants are
byte-identical to the native `kDescriptorWalHeader` / `kDescriptorWalMaxBytes`
and to the Node `DESCRIPTOR_WAL_HEADER` / `MAX_DESCRIPTOR_WAL_BYTES`; this
contract does not change either and must not be used to change either.

Only the create path may discard. `DELETE` access is requested only when this
call creates the leaf, and the disposition is set through the handle this call
already owns, so no path metadata is trusted a second time. Discarding a leaf
this call created with `CREATE_NEW` and never published is not a WAL repair: no
frame, no foreign byte, and no external observer can exist yet. The reopen path
never requests `DELETE`, never deletes, never truncates, and never writes;
failure there preserves the file exactly as found.

## Lease, handoff, and inheritance

`DescriptorWalLease` is private, noncopyable, and move-only, exposes no raw
handle accessor, and moves through `empty` → `held` → `handoff_transferred`.
At most one duplicate may be prepared; a second
`prepare_inheritable_handoff` is refused with `handoff_already_transferred`
before anything is reset, so it cannot destroy the handoff a first call
produced. The pre-duplication recheck set is exactly the acquisition check set,
and each refusal carries its own status, so a DACL regression, a size change, a
torn prefix, a path swap, a volume change, an ancestor swap, and a
handle-inheritance anomaly stay distinguishable.

The duplicate is created with `DuplicateHandle(..., GENERIC_READ | GENERIC_WRITE,
FALSE, 0)`. It is born non-inheritable, carries a strict subset of the source
handle's access, and never uses `DUPLICATE_SAME_ACCESS`. No `DELETE`, no
`WRITE_DAC`, and no `WRITE_OWNER` crosses a future process boundary.
`READ_CONTROL` does cross, because `STANDARD_RIGHTS_READ` and
`STANDARD_RIGHTS_WRITE` are both `READ_CONTROL`; that only lets the child read
a DACL naming its own user. `arm_inheritance()` and `revoke_inheritance()` are
separate, idempotent, typed steps over
`SetHandleInformation(HANDLE_FLAG_INHERIT, ...)`, and each decides on the
observed kernel flag rather than the API return.

Hard precondition on any future launcher; every clause is mandatory, and a
launcher that cannot satisfy all of them must close the duplicate instead of
launching:

1. Arm inheritance only immediately before the single `CreateProcess*` call
   that must receive this handle.
2. That call must pass an explicit handle allowlist through a
   `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` thread-attribute entry containing
   exactly this handle. `bInheritHandles = TRUE` without that allowlist is
   forbidden.
3. Revoke inheritance, or close the duplicate, immediately after the child is
   created and on every failure path.
4. `take_handle()` is refused while inheritance is armed.

This is the storage-side half of the property the supervisor launch contract
models as `no_ambient_handle_inheritance`.

`DuplicateHandle` produces a second handle to the same file object, so parent
and child share one file position. After transfer the child owns it: the lease
refuses every parent-side I/O operation with `handoff_already_transferred`, and
the child must use positional reads and writes only. A Win32 `HANDLE` is not a
Microsoft C runtime file descriptor; the duplicate must never be serialized as
`LAE_ACTION_JOURNAL_FD`, and a future reviewed bridge must convert it inside the
child.

## Accepted limitation: DELETE is retained for the create-path lease lifetime

Review item R4 is closed as an accepted design limitation, not implemented. The
reasoning is recorded in
`native/action_journal_storage/DESCRIPTOR_WAL_BOOTSTRAP.md` under "Accepted
design limitations" and is summarised by
`delete_on_failure.disarmed_before_lease_ownership` in `v0.1.0.json`: Win32
cannot narrow an existing handle's granted access, share bookkeeping lives on
the file object rather than the handle, and the restriction other processes see
is unchanged either way.

Those API contracts do not prove physical-media durability, antivirus or
filter-driver behavior, SDK compatibility, ACL or share-mode behavior on the
Dell target, `HANDLE`-to-CRT descriptor conversion, or power-loss safety.
Remote Windows compilation and static analysis, a reviewed launcher bridge, and
exact-target acceptance remain mandatory before any integration or activation.
Approval of this contract is not activation, production availability, compile,
Windows, or target approval, and advances no phase or release gate.
