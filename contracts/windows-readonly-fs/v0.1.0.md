# Inert Windows read-only filesystem boundary v0.1.0

This contract describes source for a future Windows `stat`, `list`, and bounded
UTF-8 `read` library. It is deliberately not a helper executable and has no
transport, CMake target, Node import, registry entry, package entry, or
activation path. The existing Windows filesystem refusal remains authoritative,
and production capability remains unavailable.

## Authority and traversal

A request names an opaque grant ID, an exact canonical local drive path, and an
independently issued root identity: `FILE_ID_INFO` volume serial plus 128-bit
file ID. `CreateFileW` opens only the fixed drive root with no-follow semantics
and write/delete sharing denied. Every component from that root to the grant
root is then opened relatively and retained. The final grant-root resolved
handle path, independent identity, volume policy, owner, DACL, attributes, and
directory type must all match.

Every descendant is opened one component at a time with `NtOpenFile` and an
`OBJECT_ATTRIBUTES.RootDirectory` set to the already retained parent handle.
No joined descendant path and no pathname fallback exists. Each open uses
`FILE_OPEN_REPARSE_POINT`; the resulting handle is rejected if it is a reparse
point or unsupported object. Root, intermediate, target, and reported-list-child
handles are retained with `FILE_SHARE_READ` only and revalidated before success.

The exact-current-user profile is deliberately narrow: every grant-root
component and requested/listed object (but not the fixed drive root) must be
owned by the current non-service token user and have a protected,
nondefaulted DACL containing exactly one noninherited `FILE_ALL_ACCESS` allow
ACE for that SID. This will reject ordinary inherited workspace ACLs. It is a
safe source boundary, not evidence that an operator workspace is usable.

UNC, extended/device paths, alternate streams, malformed UTF-16, slash or dot
components, reserved names, trailing dots/spaces, reparses, hardlinked files,
delete-pending objects, non-disk objects, offline/sparse/compressed/encrypted/
recall/virtual objects, non-fixed or hot-plug media, and non-NTFS filesystems
fail closed. The volume must expose persistent ACLs and every opened object's
volume serial must match the independent grant.

## Fixed operations and limits

- `stat` returns only type and bounded size for the root or one retained target.
- `list` returns at most 256 immediate entries and at most 65,536 UTF-8 name
  bytes. Every enumerated entry is component-validated, relative-opened, and
  handle-inspected before it is reported. Unsafe or raced entries fail the
  entire operation rather than being skipped.
- `read` accepts a bounded offset and returns at most 65,536 bytes from a file
  no larger than 16,777,216 bytes. It accepts only strict UTF-8. Embedded NUL
  is a binary refusal; invalid or partial UTF-8 is refused rather than repaired.

Mandatory monotonic deadline and cancellation callbacks are checked throughout
traversal, enumeration, and chunked reads. A failed or cancelled request returns
no file text, entry names, stat data, or retained lease. The finite receipt has
only status, operation, opaque grant ID, counts, truncation, and identity/handle
booleans; it never contains a root/path, SID, user name, file content, list
names, arbitrary OS error, or free-form diagnostic.

## Official API assumptions and residual gates

The source design relies on these Microsoft API contracts:

- `NtOpenFile` and `OBJECT_ATTRIBUTES.RootDirectory` relative opens:
  <https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-ntopenfile>
- object attributes and `RootDirectory` semantics:
  <https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes>
- `CreateFileW` sharing and no-follow flags:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew>
- final root path from a retained handle:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew>
- handle metadata and directory enumeration classes:
  <https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex>
- exact file/volume identity:
  <https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info>
- handle owner/DACL inspection:
  <https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo>
- fixed drive classification:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdrivetypew>
- hot-plug storage information:
  <https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-storage_hotplug_info>
- handle-associated filesystem information:
  <https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew>
- strict UTF-8 conversion flags:
  <https://learn.microsoft.com/en-us/windows/win32/api/stringapiset/nf-stringapiset-multibytetowidechar>

`NtOpenFile` is an NT native API whose SDK declarations, user-mode link/import
story, behavior under filter drivers, and target compatibility require remote
Windows compilation and exact-target testing. Source review does not prove that
an executable can safely expose it. A separately signed/pinned helper identity,
authenticated bounded transport, process-tree supervision, independent audit,
package review, filter-driver/concurrency tests, and Dell target acceptance are
all mandatory. Until those gates pass, Windows filesystem reads stay refused.
