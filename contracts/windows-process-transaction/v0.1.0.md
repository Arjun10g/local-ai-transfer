# Supervisor-owned Windows process transaction v0.1.0

This is a source-only design packet, not a process capability. The code is
inside the anonymous namespace of the existing inert Windows supervisor and
has no public entry point. It is absent from CMake, the host, tool registry,
launcher, installer, and package. Every production and process-transaction
gate is an immutable `false`; the module-private durable-journal adapter has
no implementation or installation path. Nothing in this slice can launch a
process.

The design intentionally rejects the former separate-broker boundary. A
request cannot supply a Job, process, thread, token, issuer, capability key,
or journal callback. The supervisor privately recomputes the request,
executable, restricted-token profile, argv, cwd, limit, environment, and root
generation digests; verifies and consumes a one-use capability from its own
issuer; and serializes one launch transaction. Only `SystemRoot` is supplied
to the child. There is no shell, PATH search, breakaway, detached, nested-Job,
or leader-only cleanup path.

All fallible preparation happens before journal dispatch. The existing
module-private `JournalAuthority` asks its private `DurableJournalAdapter` to
append and read back the exact start record. The next callback performs only
bounded cancel, inclusive monotonic-expiry, and retained-executable identity
checks before calling `CreateProcessAsUserW`. That call uses
`CREATE_SUSPENDED` and a `STARTUPINFOEX` attribute list containing both the
closed inherited-handle list and `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Immutable
payload arrays are owned by the attribute object through the synchronous
creation call. This requests root-Job membership from first child existence;
that Windows behavior remains uncompiled and target-unproven. An
assign-after-create fallback is forbidden.

The source creates one manual-reset cancellation event during latent supervisor
initialization. Shutdown sets it before attempting the transaction/registry
lock and carries one inclusive absolute cleanup deadline through lock wait,
process wait, Job-zero proof, and worker settlement. If any proof fails, the
root Job, registry, cancellation event, and worker contexts remain owned; the
source does not close them and claim settlement.

`shutting_down` is set before the cancellation event is signalled. Every
active-operation checkpoint, overlapped hash wait, and process-monitor loop
checks that atomic state as well as the event. Thus a failed `SetEvent` cannot
leave an already observed shutdown request invisible to later checkpoints.

After creation, the supervisor owns the process, primary thread, pipe ends,
bounded drain workers, and root Job. It verifies Job membership, reserves a
stable registry slot before transferring handles, rechecks cancellation,
expiry, and executable identity, then resumes. Output is capped before
accumulation. Success requires the primary exit, the entire root Job reaching
zero active processes, settled drain workers, and a durable terminal journal
record. Timeout, cancellation, output overflow, child/descendant ambiguity,
registry failure, drain uncertainty, and terminal persistence uncertainty
terminate the whole Job where possible and remain failure or
`dispatched_unknown`; no replay is authorized. An inability to settle owned
workers or prove the terminated Job empty is a supervisor fail-stop: process
exit closes the kill-on-close Job, and startup recovery retains the durable
start as unknown/manual rather than emitting an acknowledgement. Because the
shared root Job is the cleanup boundary, this source permits only one active
launch transaction. Drain buffers are held by explicit guarded owners: normal
object destruction fail-stops while a worker may still reference a buffer, and
only a proven joined-worker path can release it. An ambiguous shutdown cannot
let registry/static destruction free a live worker context.

Executable hashing uses overlapped reads. Once a read is pending, every
deadline, cancellation, event, and unexpected-error path cancels as needed and
waits for the exact event plus `GetOverlappedResult`; inability to prove the
specific operation settled is fail-stop, so stack event/OVERLAPPED/buffer
lifetime cannot end first. These are static source invariants, not Windows
runtime evidence.

The wrapper derives its final redacted status from both the callback receipt
and the actual durable journal outcome. A durable terminal failure replaces a
stale callback `ok` or untouched default with `terminal_failure`; any start or
terminal persistence ambiguity is `dispatched_unknown`. `journal_bound` is
true only for the exact durable terminal state, while `job_reaped` is copied
only from the cleanup proof.

The following are deliberate blockers, not implementation details to infer as
complete: the ActionJournal helper has no installed authenticated adapter;
that future adapter must own its lifetime and cooperatively settle every
authenticated call within the same absolute transaction deadline; startup
recovery has no production wiring; Windows does not create the image or cwd
from the retained handles, so executing-section and stable-cwd proofs remain
false; DLL/plugin closure is unproven; and no Windows compile, API-race,
restricted-token, parent-death, target, or acceptance evidence exists. A later
slice must solve and independently audit those dependencies before changing a
gate or adding any integration.
