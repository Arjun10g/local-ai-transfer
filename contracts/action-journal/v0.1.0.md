# Foreground action-journal protocol v0.1.0

This is a source-only, provider-independent contract for a future dedicated
foreground native journal helper. It does not select a transport, implement a
durable store, launch a process, or activate production journaling. The current
host and package do not import this module. Production availability remains
`false` on every platform until the native helper, trust anchor, packaging,
supervision, and target acceptance are separately complete.

## Frame and authenticated session

One frame is a four-byte unsigned big-endian payload length followed by exactly
that many UTF-8 bytes. The payload is one canonical JSON object. Payloads are
at most 65,532 bytes; complete frames are at most 65,536 bytes. An incremental
reader may buffer at most eight frames, and a session ends after at most 1,024
authenticated frames in either direction.

Canonical JSON uses increasing ASCII/UTF-8 byte order for the contract's fixed
ASCII object keys, no whitespace, UTF-8 strings without controls or unpaired
surrogates, and safe base-10 integers only. All valid protocol string domains
are exact ASCII patterns or finite enums. Floating point, negative zero,
duplicate keys, unknown keys, alternate key ordering, malformed UTF-8,
trailing bytes, and over-limit objects/arrays/strings are rejected.

The future supervisor provisions a fresh 32-byte key and a fresh 16-byte
session nonce out of band. They never appear in argv, environment, logs, or a
receipt. Every envelope contains the lowercase hexadecimal nonce and a
per-direction sequence beginning at zero. The receiver requires the exact
nonce and next sequence. Request IDs are unique for the bounded session; a
duplicate ID or old sequence is replay, while a future sequence is
`sequence_out_of_order`.

Responses are lockstep-correlated to an already queued request: request ID,
method, operation ID (except the helper-created ID returned by `prepare`),
query bounds, cursor/event ordering, and the request deadline must all match.
An unsolicited, reordered, late, or otherwise unbound response is rejected.

The 32-byte HMAC is:

```text
HMAC-SHA256(key,
  "lae.action-journal.v0.1.0" || NUL ||
  canonical-json(envelope with mac omitted))
```

The synthetic key in `v0.1.0-vectors.json` is fixture material only.

Requests carry absolute `issued_at_ms` and `deadline_at_ms` Unix times. The
deadline must be later than issue time and no more than ten minutes later.
Receivers reject expired requests and issue times more than 30 seconds in the
future after authenticating the envelope.

## Exact methods

| Method | Operation ID | Exact request body | Successful state/result |
|---|---|---|---|
| `health` | null | `{}` | availability/status only; `production_enabled` is false in this slice |
| `prepare` | null | tool/risk/side-effect plus five opaque SHA-256 digests | helper-created ID, `prepared` |
| `authorize` | required | `authorization_kind` | `authorized` |
| `dispatch` | required | `{}` | `dispatching` durable barrier |
| `acknowledge` | required | `provider_receipt_digest` | `acknowledged` |
| `begin_reconciliation` | required | finite `reason` enum | `reconciling` |
| `complete` | required | `receipt_digest`, completion `resolution` | `completed` |
| `cancel` | required | denial/cancellation `resolution` | `cancelled` |
| `fail_definitive` | required | definitive `resolution` | `failed_definitive` |
| `mark_unknown` | required | `dispatch_ambiguous` | `unknown_manual` |
| `summary` | null | bounded cursor/limit/include-terminal query | bounded redacted receipt page |
| `detail` | required | bounded after-sequence/limit query | bounded redacted event page |

The transition graph is exact: `prepare` creates `prepared`; only `prepared`
may authorize; only `authorized` may dispatch; dispatch may acknowledge,
reconcile, or become unknown; acknowledged may complete, reconcile, or become
unknown; reconciling may complete, fail definitively, or become unknown; and
unknown may be resolved only to completed or failed definitive. Terminal states
never transition.

## Failure and recovery semantics

`dispatching` is a durable pre-provider barrier. Loss of a dispatch response
does not permit another dispatch; after transport loss the client establishes
a fresh authenticated session and uses `detail`. A provider timeout or lost
provider acknowledgement enters reconciliation or `unknown_manual`.

`complete` contains a future internal noncancellable durable commit. A cancel
that races that section returns only `commit_non_cancellable`; the caller then
queries `detail`. It neither rewinds completion nor authorizes a replay.

On startup, `prepared` and `authorized` become `cancelled` with
`startup_recovery`. `dispatching`, `acknowledged`, and `reconciling` become
`unknown_manual` with `dispatch_ambiguous`. Terminal and already-unknown records
remain unchanged. Recovery never guesses whether an external effect happened.

Success responses contain only a redacted receipt or bounded pages of redacted
receipts/events. A receipt contains operation ID, state, per-operation sequence,
authorization kind, finite resolution, recovery-required boolean, and a digest.
It contains no arguments, previews, provider payloads, message/file content,
URLs, command output, credentials, session keys, or session nonce. Errors carry
an empty body, null state, and only a finite code with its contract-fixed
retryability. Even these binding
receipts are host/operator data and must not enter model history.

The machine-readable contract and deterministic request/response frames are in
`v0.1.0.json` and `v0.1.0-vectors.json`.
