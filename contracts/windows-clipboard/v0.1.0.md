# Inert direct Win32 clipboard boundary v0.1.0

This contract describes source that is intentionally unreachable in the
product. It is absent from CMake, host registries, packaging, and launch paths.
Its supervisor, authenticated capability issuer, cancellable-I/O boundary,
durable journal, and target-acceptance constants are all immutable `false`.
Consequently the public entry points return `platform_unavailable` before
reading request pointers or touching clocks, sessions, windows, clipboard
state, allocation, or the journal. There is no runtime override.

## Authority and session boundary

The future broker-issued capability is opaque and nonconstructible in this
slice. Its reserved MAC covers the exact operation, assistant session,
interactive Windows session, issuance and expiry ticks, journal operation ID,
request/content/confirmation digests, confirmed clipboard sequence, the
explicit all-format replacement bit, and an authority nonce. The MAC value is
the authenticator and is not recursively included in its own bound-field
frame. A separate, nonconstructible authority object owns the unexposed issuer
key and nonce. It recomputes HMAC-SHA-256 over the versioned binary frame and
compares both the nonce and MAC in constant time. This source has no issuer,
deserializer, setter, test constructor, or key-provisioning path, so no valid
authority object can be created here.

A latent execution path accepts only the active local console session on the
`WinSta0\Default` input desktop. It cross-checks process-ID session, token
session, active-console session, process window station, current thread
desktop, and input desktop. Remote, service, disconnected, non-default, and
ambiguous sessions refuse. Independent window-station and input-desktop
handles are retained for the whole operation, preventing the attested named
objects from being destroyed and replaced while the lease exists. Bounded
name/type/object-flag plus owner/group/DACL security-descriptor fingerprints
must match the process station, thread desktop, retained handles, and freshly
opened station/input handles; `UOI_IO` must still identify the retained and
fresh desktop as the active input desktop. These checks run around
`OpenClipboard`, immediately before `EmptyClipboard`, before and after final
close, and before read/status publication. The assumptions still require exact
Windows security review and target race testing.

## Read contract

`clipboard.read` is T1 and reads only `CF_UNICODETEXT`. Opening uses bounded
retry/backoff under one monotonic five-second capability deadline and a future
supervisor-owned cancellation event. `GlobalSize` is bounded before
`GlobalLock`; the buffer must contain a terminator and valid UTF-16 scalar
sequence. Conversion uses strict Windows UTF-8 flags and the returned UTF-8 is
limited to 65,536 bytes. Sequence checks surround the snapshot. The text may
appear only in the tool result; receipts, errors, and default logs contain
only operation/status/size/sequence and fixed booleans.

## Confirmed write contract

`clipboard.write` is T2. Windows requires `EmptyClipboard` before publishing
the replacement `CF_UNICODETEXT` object, which clears every existing format.
The confirmation therefore must explicitly disclose and authorize complete
clipboard replacement. Authority binds the exact content digest and the
sequence shown in that preview; if the sequence changed, the write refuses.

Length, embedded-NUL, and strict UTF-8 checks occur before content hashing;
conversion occurs before dispatch. The source allocates one
bounded zero-initialized moveable global object, writes an exact terminated
UTF-16 sequence, wipes its temporary wide buffer, and unlocks it. Immediately
before mutation it checks cancellation/deadline once and requires a durable,
exact journal dispatch. It then revalidates the retained OS-object identity
immediately before `EmptyClipboard`; a mismatch is durably recorded as
failed-before-mutation. An already-dispatched operation never calls
`EmptyClipboard` or `SetClipboardData`.

After durable dispatch the commit is noncancellable. Before the first
`EmptyClipboard` call, the journal must durably record a mutation-prepared
marker; failure to save that marker refuses the call. The response uses the
closed tri-state `mutation_attempt_state`, never a boolean. Dispatch or a
mutation-prepared marker without terminal evidence is
`may_have_been_attempted`, including after restart. `attempted` is published
by the live process only after `EmptyClipboard` returned, or reconstructed
from a durable terminal state that necessarily follows that call.
`not_attempted` is reserved for not-dispatched or durable
failed-before-mutation evidence. The broker then attempts `EmptyClipboard`
and `SetClipboardData(CF_UNICODETEXT, ...)` without misreporting cancellation
as non-mutation. It retains and frees the global object until
`SetClipboardData` succeeds; after success Windows owns it. Close and
sequence correlation precede a durable typed outcome. Failure
after clearing, close ambiguity, sequence ambiguity, or outcome persistence
failure returns `mutation_unknown` and must never trigger an automatic replay.
The durable outcome distinguishes a desktop refusal before the destructive
call from an `EmptyClipboard` call that was attempted but reported failure, so
status queries cannot falsify the mutation-attempt state.
The retained desktop proof is checked again after clearing and before
`SetClipboardData`, then before and after close. A mismatch after mutation is
recorded as unknown and can never be replayed. An unlock, free, or
clipboard-close failure is a sensitive cleanup ambiguity:
the future dedicated helper must fail-stop rather than continue or publish a
successful receipt.

## Lost acknowledgement

`clipboard.write.status` is read-only. It binds lookup to the same operation
and request digest. A durable `applied` record may answer complete. A
dispatch-only, mutation-prepared, or unknown-after-mutation record may compare
current sequence and exact content, but can report only
`postcondition_present_manual` or
`postcondition_absent_manual`; it cannot attribute the volatile clipboard
state strongly enough to invent completion and never repeats the write. It
revalidates the retained desktop/session immediately after journal lookup and
again after any later blocking journal outcome call. It performs a final
cancellation/deadline and identity probe immediately before publishing either
a durable or volatile status result.

## Remaining gates

Independent review, a real module-private authenticated issuer/key provisioner,
an approved supervisor-owned cancellation primitive, durable ActionJournal
adapter, remote Windows compilation/static analysis, exact desktop/session and
clipboard-concurrency tests, package review, and target acceptance are all
required. This contract does not make clipboard functionality available and
does not advance any product or release gate.
