# Local Assistant Engine — Five-Session Execution Pack

## Purpose

This pack is the execution plan for a **fully local, portable laptop assistant** whose language model runs from a verified model file already present on the target Dell Windows laptop. Core inference must not require Internet access, Docker, Ollama, a public model hub, public package registries, a target-side compiler, or a cloud model. Network tools may be enabled explicitly, but chat, local tools, caching, and the UI must continue to work when the network is disconnected.

The plan uses exactly five coding-model sessions:

| Session | Required model | Function |
|---|---|---|
| Session 0 | **GPT-5.6 Sol** | Orchestrator, planner, reviewer, integrator, conflict resolver, and release-gate owner |
| Session 1 | **GPT-5.6 Luna** | Native runtime, model lifecycle, local API, streaming, cancellation, and session-state implementation |
| Session 2 | **GPT-5.6 Luna** | Model artifact pipeline, Intel hardware probing, CPU/Vulkan/SYCL evaluation, caching, and performance |
| Session 3 | **GPT-5.6 Luna** | Assistant loop, structured tool calling, laptop tools, web tools, UI, and process supervision |
| Session 4 | **GPT-5.6 Luna** | Independent correctness, security, fuzzing, Shadeform execution, packaging, and release evidence |

Sol directs and reviews the work. Luna sessions perform nearly all coding, experiments, profiling, debugging, test construction, and documentation.

## Fixed MVP model

The model decision is now:

- **Model:** Qwen3.5-9B
- **Artifact:** project-produced `Qwen3.5-9B-Q4_K_M.gguf`
- **Source:** approved, pinned copy of the official Qwen3.5-9B weights
- **Format:** text-only GGUF; no vision projection in the MVP package
- **Expected artifact envelope:** approximately 5–6 GiB; the exact byte size and SHA-256 are generated by the controlled Shadeform build
- **Default behavior:** thinking disabled for normal conversation and tool routing
- **Optional behavior:** bounded thinking enabled for explicitly complex tasks
- **Default context:** 8,192 tokens
- **Maximum MVP context:** 16,384 tokens only after memory, correctness, and latency gates
- **Quantization position:** Q4_K_M is treated as a high-quality memory/performance compromise, not as automatically lossless

The accepted GGUF is not downloaded on the target laptop. It is created and evaluated on Shadeform, transferred through the approved path, and accepted only when its manifest, hash, architecture, tokenizer, template, and quality evidence match.

## Intel GPU position

The user has confirmed that the Dell laptop has an Intel GPU, but “Intel GPU” is not a sufficiently precise hardware specification. The exact GPU could range from an older integrated adapter to a recent Intel Arc/Xe device, with very different driver, memory, and kernel behavior.

The runtime policy is therefore:

1. **CPU is the mandatory correctness and fallback backend.**
2. **Vulkan is the primary accelerated candidate** when the exact Intel adapter and driver pass the probe and correctness suite.
3. **SYCL is experimental**, not the default. It must independently earn promotion through parity, stability, and speed evidence on the exact device.
4. **No backend is selected from the vendor name alone.** The launcher consumes a signed/hashed hardware receipt and an approved backend profile.
5. **The release contains a safe CPU binary and an Intel Vulkan binary.** A SYCL binary is included only when it is fully self-contained, approved, and measurably useful.

See `governance/INTEL_GPU_BACKEND.md` for the full decision tree and commands.

## Product architecture

The MVP is a repository-owned product, not a loose script around an installed desktop application:

1. A self-contained Windows x64 native executable built around a **pinned, source-vendored, narrowly exposed llama.cpp/ggml substrate**.
2. A repository-owned backend interface so CPU, Vulkan, and experimental SYCL profiles can be tested without changing the assistant layer.
3. A repository-owned OpenAI-compatible loopback API and a separate event-rich assistant API.
4. A zero-runtime-dependency Node.js 24 host using built-in modules only.
5. A strict, auditable tool dispatcher with path boundaries, argument schemas, confirmation gates, timeouts, and output caps.
6. A portable release ZIP built remotely, with model weights transferred separately.

Upstream llama.cpp is used as the correctness/performance oracle and source substrate; the target user does not install llama.cpp.

## Start the five sessions

1. Put this directory at the root of a new repository.
2. Start GPT-5.6 Sol with `sessions/00_SOL_ORCHESTRATOR.md`.
3. Sol creates the blackboard/coordination files and freezes the initial contracts before implementation begins.
4. Start four separate GPT-5.6 Luna sessions with:
   - `sessions/01_LUNA_RUNTIME.md`
   - `sessions/02_LUNA_MODEL_PERFORMANCE.md`
   - `sessions/03_LUNA_AGENT_TOOLS.md`
   - `sessions/04_LUNA_QA_RELEASE.md`
5. Give the five sessions access to the same repository through separate branches/worktrees.
6. Every session reads `AGENTS.md`, `CONTEXT.md`, and the governance documents before changing code.
7. Sol alone merges to `main` and declares phase gates complete.

When sessions cannot share a filesystem, all handoffs must use the committed templates and include exact commit identifiers. No decision may exist only in a private chat.

## Non-negotiable boundaries

- No model download occurs on the target laptop.
- No model weight file is committed to Git.
- The target runtime never silently uses a cloud model.
- The first release does not require Docker, WSL, administrator rights, a compiler, CUDA, Python packages, or npm packages.
- Formal model conversion, quality tests, performance tests, backend tests, and release builds run on Shadeform.
- A final read-only hardware probe and launch/acceptance check occur on the target laptop.
- The server binds only to loopback and uses an ephemeral local authentication token.
- The runtime remains a foreground process and installs no service, scheduled task, daemon, or startup item.
- Local file contents are never sent to an Internet tool without a clear disclosure and confirmation.
- One deployable model only. Workers may not swap models to make a failing benchmark pass without a Sol-approved ADR.
- GPU acceleration is never accepted merely because the process launches; output parity, repeated-turn stability, long-prompt stability, cancellation, and memory recovery must pass.

## Definition of offline

Offline means model loading, tokenization, inference, chat state, local file/system tools, and the UI work after network interfaces are disabled. A web search or page fetch requires a configured network provider; without it, the tool returns a typed `network_unavailable` or `provider_unconfigured` result and the local assistant continues operating normally.
