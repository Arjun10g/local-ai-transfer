Every placeholder makes the manifest invalid. The artifact job must replace all placeholders with exact values before the verifier or release gate accepts it.

## Why no hash or byte count is prefilled

This plan does not point the target at an arbitrary community quant. The accepted GGUF is generated from a pinned official source revision with a pinned conversion toolchain. Its exact bytes, byte count, tensor inventory, and SHA-256 therefore exist only after that controlled job completes. Guessing or copying a hash from another artifact would defeat provenance verification.

## Required identity and provenance

The generated manifest must record:

- Stable model and artifact IDs.
- Official source repository and exact immutable revision.
- Archived model-card and license hashes.
- Exact conversion and quantization tool revision.
- Exact command and environment receipts.
- Exact GGUF byte count and SHA-256.
- GGUF metadata and tensor-inventory digests.
- High-precision or Q8 comparator artifact ID.
- Artifact scan, transfer, and approval references.

## Structural validation

The verifier must compare the artifact with the accepted Qwen3.5-9B language-model profile. At minimum it checks:

- GGUF magic and supported version.
- `qwen35` architecture metadata or the exact equivalent emitted by the pinned accepted converter.
- 32-layer hybrid structure.
- Expected attention and recurrent tensor families.
- Expected dimensions, element counts, offsets, alignments, and file bounds.
- Eight full-attention layers and the accepted Q/KV-head profile.
- MTP metadata/tensors, whether enabled or intentionally unused at runtime.
- No requirement for an external vision projection in the text-only profile.
- Finite, allowlisted tensor storage types compatible with the accepted `Q4_K_M` recipe.
- Tokenizer, special tokens, stop tokens, chat template, tool-call fixtures, and thinking-control behavior.

The verifier reads dimensions from metadata and the tensor inventory; inference code must not assume that a filename proves identity.

## Runtime validation behavior

`verify-model` must:

1. Parse the manifest with a strict schema and unknown-field policy.
2. Reject placeholders, zero/negative sizes, malformed hashes, and unapproved revisions.
3. Validate manifest trust or attestation when configured.
4. Canonicalize the model path and enforce the approved local model root.
5. Confirm regular-file identity and exact byte count.
6. Compute SHA-256 and compare it with the manifest.
7. Parse GGUF metadata with bounded reads before large allocations.
8. Validate architecture, dimensions, tensor inventory, tokenizer, template, and modality profile.
9. Produce a metadata-only local verification receipt.
10. Refuse load on any mismatch.

A production `--skip-model-verification` switch must not exist.
