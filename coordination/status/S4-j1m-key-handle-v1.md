## Problem

`validate_persisted_argv` (`991b70e`) accepts the `-i` operand of a persisted
argv only when it is a canonical private handle: a basename matching
`_HANDLE_BASENAME`, an ordinary single-link file owned by this process at mode
`0600`, an owner-private direct parent, and no group/world-writable ancestor.
`sf.create_keypair` wrote `id_ed25519` into a system `TemporaryDirectory`, which
satisfies neither the basename nor the ancestor rule. `_remote` validates every
command, so **every** ssh and scp argv in `execute()` was refused before it
could spawn — after an instance had been created and billed.

That was the third refusal of this shape found by reading source. It is the last
one that will be found that way.

## What changed

### 1. Where the ephemeral key lives

`.secrets/j1m/<run-id>-<ownership-nonce>/ssh-key`, mode `0600` inside a `0700`
directory, generated by `ssh-keygen -t ed25519 -N '' -q -f <path>` as an argv
array with a sanitised child environment; the public half is uploaded exactly as
before.

Why the validator trusts it: `_private_handle_snapshot` has no trusted-root
concept of its own — it requires the *direct parent* to be owner-private and
every ancestor above it to be owned by root or this user with no group/world
write bit. `.secrets/` is the protected, Git-ignored, owner-private area
established by `b306665` for the mutation env projection, so the per-run
directory and `.secrets/j1m` are created `0700` and the checkout's ancestors
satisfy the weaker rule. `experiments/runtime/j1m-keys/` was considered and
rejected: the mocked-execute isolation treats every path under `RUNTIME_ROOT` as
operator evidence and fails any test that touches it, so a key there would be
untestable. Being under `PRIVATE_OUTPUT_ROOT` as well is not required by this
validator but keeps the key inside the same trust boundary as every other
private output.

Never reused: the directory is named from the run id plus this run's fresh
ownership nonce, and `create_keypair` refuses a directory that already exists —
the filesystem enforces one key per run. An existing ancestor that is not
owner-private is refused rather than `chmod`-ed.

Always destroyed: `destroy_ephemeral_key_directory` overwrites each file with
random bytes, `fsync`s, truncates, unlinks, and removes the directory. It runs
in `execute()`'s teardown `finally` on the success path and every failure path,
and again directly if key generation itself fails outside the protected region.
It never raises and never prints; the run receipt records
`ephemeral_key_cleanup` as status, file count and a run label — no paths into
key material, no key bytes.

Refused before spending: `sf.assert_persisted_argv_handle` proves the key
against the exact argv policy immediately after generation and before the first
billable provider call.

### 2. Two more operands in the same class, fixed at the operand

- `--token-file /scratch/j1m/engine-token` named a path on a host this process
  has not contacted; `token-file` is a private-handle option, so no *local*
  canonical-handle proof can ever exist for it and the whole eval command was
  refused. Renaming the option to dodge its credential detector would be
  obfuscation and loosening the detector would weaken a real control, so the
  orchestrator stops naming a credential path it cannot prove:
  `remote_model_eval.py` creates its bearer token in an owner-private temporary
  directory of its own.
- `"token_logging": false` in the eval receipt is credential-shaped (`_token_`),
  so `validate_persisted_output` — which the descriptor-safe publisher applies
  to every byte — rejected the entire serialized receipt. A paid eval produced
  an eval receipt that could never be published. Renamed to `tokens_logged`.

### 3. Salvage review fixes (`J1M-SALVAGE-TRANSPORT-001`)

- **MAJOR 1 — build mode.** Eight schema-bound JSON receipts (`manifest.json`,
  `tensor-metadata.json`, `source-model-receipt.json`,
  `conversion-receipt.json`, `model-receipt.json`, `toolchain.json`,
  `scan-receipt.json`, `post-cleanup-receipt.json`) are now carried by the same
  bounded transport. Three configured names stay uncarryable with their own
  typed reason `salvage_refused_non_receipt` and a refusal class: the GGUFs
  (`weights` — not evidence, never pulled to the laptop), `checksums.sha256`
  (not JSON) and `command-receipt.json` (a JSON *array*, so it can hold neither
  a top-level schema nor the required binding). Build mode now sets
  `receipt_error` and `status = failed` when a source-allowlisted receipt does
  not land. Prove mode gets the same rule, which it also lacked — it set
  `receipt_error` without setting `status`.
- **MAJOR 2 — required identity binding.** `execute()` writes
  `run-identity.json` and uploads it to the single source-fixed path
  `/scratch/j1m/run-identity.json` after the config upload and before any
  receipt-producing command; a failed upload fails the run. Every host-side
  writer — `j1m_runner`'s nine receipt writers plus `remote_model_eval.py`,
  `remote_eval_prepare.py`, `remote_toolchain_probe.py` and
  `cuda_device_probe.py` — reads exactly that path and stamps `run_id` and
  `instance_id` into its receipt. The transport now **requires** both on every
  allowlisted name (`salvage_identity_missing` / `salvage_identity_mismatch`),
  and artifact-identity claims are required where the receipt declares them.
  **Deliberate consequence:** the receipts' *content* changes while the remote
  command plan does not — the binding travels in an uploaded file, not in argv,
  so `_eval_remote_commands` and `_remote_job_command` are byte-identical to the
  reviewed versions. The receipt fixtures in `test_j1m_lifecycle.py` and the
  strict key-set checks in `j1m_runner._validate_producer_receipts` were updated
  for that content change, deliberately. The post-publication verifiers
  (`_verify_eval_receipt` and friends) *accept* the binding without re-demanding
  it: required-ness is load-bearing at the fetch boundary, before untrusted
  bytes are published, and re-demanding it downstream would only force fixtures
  to carry a field those verifiers do not verify.
- **MINOR — host-key re-proof.** `acquire_pinned_host_key` records the SHA-256
  of the bytes it pinned; salvage compares that digest instead of a line count,
  and the receipt records which proof was used (`host_key_reproof`).
- **MINOR — disk bound.** The whole call is refused unless free space is at
  least twice the worst-case total, because `scp` streams into staging before
  any size check can run.
- **MINOR — IPv6.** The endpoint is proved IPv4 rather than assumed;
  `salvage_endpoint_not_ipv4` replaces a malformed operand and an opaque error.
- **NITs.** The caps block now states the numbers that actually decide (per-file
  = the 2 MiB decoder bound, total = files x per-file, plus the free-space
  bound). A transport refusal with unreadable stderr is typed
  `salvage_transport_refused` rather than collapsed into a generic failure.

### 4. The pre-launch gate

`scripts/j1m_dry_run.py` drives the real `execute()` for every mode against a
fake provider and a subprocess shim that records argv instead of running it. See
design note §11 for the full contract. The live-run lane runs it as its final
step before `--execute`; exit status is `0` only when all fourteen checks pass.

Running it found two further defects that reading had not:

- `_persist_lifecycle` referenced an undefined `MAX_RECEIPT_BYTES` and raised
  `NameError` on every call since `8e3f599`. Both call sites swallow evidence
  failures so cleanup can never be stranded — which is right, and meant the
  orchestrator has never written a lifecycle receipt.
- The default `--artifact-destination` (`artifacts/qwen35-9b`, mode `0755`)
  fails the descriptor walk the salvage publisher performs, and it failed inside
  the teardown `finally` where the whole salvage call is swallowed. `execute()`
  now proves the destination before anything is billable, creating missing
  components `0700` and refusing an existing non-private one with the exact
  `chmod` that fixes it.

## Operator precondition

Git does not record directory modes, so on a fresh checkout
`artifacts/qwen35-9b` is `0755` and salvage cannot publish into it. Before a
live run: `chmod 700 artifacts artifacts/qwen35-9b`. The dry run names this as
`operator_artifact_destination_is_salvage_ready` and fails until it is done;
`execute()` refuses before any billable call with the same remedy.

### The gate proves the bug before it proves the fix

With `create_keypair` restored to the old system-tempdir layout
(`test_the_old_key_location_makes_the_gate_fail_loudly` does exactly this):

| | Status | argv recorded | argv refused | Failed checks |
|---|---|---|---|---|
| Before (key in system tempdir, `--mode eval`) | **FAIL** | 3 | 1 | `argv_validator_accepts_every_command`, `receipts_carry_required_identity` |
| After (all three modes) | **PASS** | 81 | 0 | none |

Three argv, not eighty-one: the run aborts at the first workspace stage, which
is exactly what a paid run would have done after creating the instance.
